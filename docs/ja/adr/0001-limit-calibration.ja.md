# ADR-0001: 実利用枠の校正 — /usage の手動読み取り + 429 の受動捕捉

- Status: Accepted
- Date: 2026-08-08

## Context

GUI の週次予算モニタ（claude-usage-lens-gui v0.1.6+）は、週次の消費量を
**利用者が仮定した予算**と比べて追跡している。実際のサブスクリプション利用枠は
ローカルのデータからは知り得ないためである。利用者から、*本当の*残量を
「ログから明確な数値として」収集できないかという問いがあった。

調査（2026-08-08、実際のローカルデータ）で以下が確定した:

- **先回りして利用枠の状態を持つローカルファイルは無い。** トランスクリプト
  （`~/.claude/projects/**/*.jsonl`）が記録しているのは `message.usage` の
  トークン数だけである。`~/.claude.json` と `stats-cache.json` が持つのは
  フィーチャーフラグのキャッシュとローカル集計である。`utilization` /
  `resets_at` に相当する値は、ディスク上のどこにも存在しない。
- トランスクリプト中でレート制限に近い唯一のフィールドは、
  `type:system, subtype:api_error` レコードの `error.rateLimits` である。
  調べたコーパスでは 30 件すべてが `null` で、いずれも 529 (Overloaded) か
  ネットワークエラー由来だった。このフィールドが埋まるのは、実際に 429 の
  制限拒否が起きたときだけと見られる。つまり**事後的**な信号であり、残量計
  ではない。
- 正となる数値はサーバー側にあり、Claude Code の `/usage` 画面に現れる。この
  画面は**文書化されていない** OAuth エンドポイント
  `GET https://api.anthropic.com/api/oauth/usage` を叩いている。応答は
  ウィンドウごとの消費率とリセット時刻（5-hour、7-day、7-day-Opus）である。

## Decision

非公開エンドポイントは**呼ばない**。代わりに、公式に露出している 2 つの経路から
実数を得て、それで既存のモデルを*校正*する。

### 1. 公式の `/usage` 画面からの手動校正

利用者が折を見て Claude Code の `/usage` 画面から公式の消費率を読み取り、
記録する:

```
claude-usage-lens calibrate add --utilization 45 --resets-at 2026-08-13T09:00
```

校正点（観測時刻 `t`、消費率 `u` %、次のリセット `R`）から、実効的な週次上限を
自前のストアに対して導出する:

```
window_start = R - 7d           (must contain t)
cap = consumption(window_start … t) / (u / 100)
```

計算は GUI が持つ**両方の基準**で行う — 想定コスト (USD) と input+output
トークンである。上限は**問い合わせ時**に導出し、固定しない。後の `reprice` や
新たに取り込んだ履歴が、自動的に精度を上げる。

導出される上限は**ローカルから見える実効上限**である。消費量に数えられるのは、
ローカルログが見ている分（Claude Code + Cowork）だけである。claude.ai の Web /
モバイルチャットの利用はこちらから見えないが、校正がそれを吸収する — 全体に
対するローカルの割合がおおむね一定であるかぎり、`local_consumption / cap` は
公式の割合に追従する。これは作りからして自己整合であり、校正をやり直せば基準が
引き直される。

新しい `limits` コマンドは、最新の校正から現在のウィンドウの状態を報告する:
ウィンドウの境界（`R` を基点としたリセット周期）、導出された上限、ここまでの
消費量、推定消費率 %、残りの余裕である。

### 2. トランスクリプトからの 429 制限イベントの受動捕捉

`ingest` は、`status` が 429 であるか `rateLimits` が非 null である
`system/api_error` レコードも抽出し、新しい `limit_events` テーブルに入れる
ようになった（キーはレコードの `uuid`、生の `rateLimits` JSON はそのまま保存
する）。429 は「この瞬間に消費率 = 100 %」という ground truth の観測である。

`rateLimits` が埋まった実例が**1 件も無い**ため（スキーマ不明）、v1 はこれらの
イベントを記録して見せるだけにし（`limits` が現在のウィンドウ内のものを列挙
する）、校正点への自動変換はしない — イベント単体では、*どの*ウィンドウ
（5-hour か週次か）が尽きたのかを語らないためである。どの制限に当たったかを
利用者が分かっていれば、校正にするのは 1 行で済む:
`calibrate add --utilization 100 --at <event-ts> --resets-at <shown reset>`。
実際のペイロードを観測できた時点で、自動変換を足せる。

### GUI との統合

GUI は薄いフロントエンドのままにする。校正が 1 件以上あれば `limits --json` を
描画し（バッジ: *calibrated*）、無ければ手動の予算に戻る（バッジ: *assumed*）。
設定のフィールドで観測した % とリセット時刻を入力でき、その入力は
`calibrate add` を呼び出す。

### スコープの選択

- v1 は**週次ウィンドウのみ**。5-hour のウィンドウはリセットが速すぎて、手動の
  校正では意味を保てない。後から足せるよう、スキーマには `window` カラムを
  残している。
- v1 の制限イベントは**`code` ソースのみ**。Cowork の取り込みは `audit.jsonl`
  （コストの ground truth）を読み、トランスクリプトファイルは意図的に流し読み
  しない。まれな 429 イベントのためだけに走査するのは I/O に見合わない。
  Cowork の制限イベントが重要になれば、後から広げる。
- CLI と GUI は同時に出す（相互に補強する変更である: CLI が `limits --json` を
  出し、GUI がそれを消費する）。

## Alternatives considered

- **OAuth の usage エンドポイント（`/api/oauth/usage`）** — 実際の割合が得られ、
  利用者の手間はゼロ。**利用者の判断で不採用**: 非公開・文書化されていない API
  で、いつ壊れても遮断されてもおかしくない。加えて、呼び出し元に対して積極的に
  429 を返す（既知の問題）。さらに Keychain のトークンへのアクセスが要る。
- **`/usage` の TUI をスクリーンスクレイプする** — エンドポイントより明確に
  脆い。不採用。
- **Admin Usage & Cost API** — 公式だが、対象は組織の API キー課金だけで、
  Max / Pro のサブスクリプションのウィンドウは含まない。該当しない。
- **OTEL のテレメトリエクスポート** — 公式だが、出てくるのは既に手元にある
  トークン / コストのカウンタで、利用枠の状態は乗っていない。該当しない。
- **何もしない（仮定した予算のまま）** — モニタは推測のままで、Anthropic が
  制限を変えたとき（例: プロモーションで +50 % の週）に大きくずれる。安価な
  human-in-the-loop の校正を採ることにして不採用。

## Risks

- **校正が古びる** — 利用者が `/usage` を読み直さないうちに、公式の制限が変わる
  ことがある（プロモーション、プラン変更）。緩和策: `limits` は校正の経過時間を
  印字し、GUI もそれを表示する。校正のやり直しは 10 秒で済む作業である。
- **ローカル利用の割合が安定しない** — claude.ai のチャットが大半を占める週が
  あれば、導出される % は公式の値から遅れる。受け入れる: 校正のやり直しで基準が
  引き直され、失敗の形（安全側または楽観側へのずれ）は、利用者が次に `/usage` を
  覗いたときに見える。
- **`rateLimits` のスキーマが不明** — 生のまま保存して一切解釈しないので、将来
  スキーマが変わっても取り込みは壊れない（最悪でも、イベントの情報量が少ない
  だけである）。
- **消費ゼロでの校正は定義できない** — `calibrate add` は `utilization ≤ 0`、
  ローカル消費が無いウィンドウ、観測時刻とリセット時刻が 7 日以上離れている組を、
  明確なエラーで拒否する。
